**Date:** 2026-09-25
**Scope:** End-to-end trace of AUTHENTICATED USER → BUSINESS PROFILE → BRAND → BRAND ASSETS → PRODUCT → PRODUCT IMAGE → BUSINESS BRAIN → CAMPAIGN CREATION → CONTEXT ASSEMBLY → AI PIPELINE → TRUTH CHECK → PERSISTENCE → HISTORY → PREVIEW → DOWNLOAD → REGENERATION.
**Method:** I read the current source code directly. I ran nothing: no emulator, no deploy, no browser. I treated the `docs/PHASE_*` reports as claims to check, not as facts. Every finding below cites `file:line` from the working tree at commit `b129ab7`. I made no source edits.
**Companion:** `docs/COMPLETE_CAMPAIGN_FLOW_FIX_PLAN.md`

Status legend: **WORKING**, **PARTIALLY_WORKING**, **BROKEN**, **MISSING**, **BLOCKED** (stopped by config, IAM or pricing outside the code path), **UNKNOWN** (needs a live or emulator run to settle).

## 1. Executive summary

**Overall severity: CRITICAL.** The owner's report that the flow is broken is confirmed. It is not one bug. The flow has several separate breaks, and each one stops a normal customer journey on its own:

1. **New users cannot generate at all (BLOCKED by config).** The free plan grants 100 credits a month (`functions/src/config/pricing.ts`, `free.monthlyCredits: 100`, granted at signup in `onUserCreated.ts:44,80`). One campaign costs `100 + 2×20 = 140` (`usageControl.ts:537`, and the frontend estimate `ESTIMATED_CAMPAIGN_GENERATION_CREDITS = 140` at `src/features/campaign/constants.ts:230`). Every new account therefore sees "You don't have enough credits" (`CampaignWizard.tsx:377-379`). I did not change pricing; the owner has to decide this.
2. **The browser gives up on generation after 70 s while the server keeps going.** `generateCampaignStrategy` runs the whole 12-stage pipeline inside one callable (`generateCampaignStrategy.ts:222-515`). The client calls it through `httpsCallable` with no `timeout` option (`src/services/api.ts:18`), so the Firebase JS SDK default of 70 s applies. The pipeline makes about 10 sequential Gemini calls plus one DALL-E 3 HD call, so it will usually take longer. The wizard then shows "We couldn't start this campaign. Any reserved credits have been returned." (`CampaignWizard.tsx:411`), which is false: the server keeps running and charges the credits. The wizard also rotates the idempotency key (`:421`), so a retry becomes a second paid generation.
3. **Campaign assets overwrite each other across all tenants.** The pipeline gives assets fixed IDs: `asset_headline_0`, `asset_poster_0`, `asset_whatsapp_0` and so on (`pipeline.ts:1047-1173`). `createCampaignAssets` writes them to `campaign_assets/{assetId}` (`firestore.ts:350-359`). Every new campaign from any business therefore overwrites the previous campaign's asset documents. Older campaigns lose their assets from history, and two concurrent generations mix their outputs.
4. **The campaign detail page probably cannot read its assets.** `campaignAssetService.listByCampaign` queries `campaign_assets` filtered only by `campaignId` (`src/services/database.ts:318-327`). The read rule (`firestore.rules:161-169`) depends on `resource.data.userId`, which assets never have, or on `resource.data.businessId in token.businessIds`, which the query does not constrain. Firestore rules are not filters, so the whole query should be denied. The detail page wraps it in `Promise.all` and shows "Something got in the way" (`src/app/campaigns/[campaignId]/page.tsx:65-68,100-102`). This is high-confidence but not live-verified. Phase 19C already flagged it as NOT VERIFIED (`docs/PHASE_19C_RECAPTCHA_APPCHECK_VERIFICATION_REPORT.md`, "Other open items").
5. **Brand Kit save is broken.** `/brand` writes straight to Firestore from the client with the form's `logo` field (`src/app/brand/page.tsx:168,419`). With no logo, that field is `undefined`, and the client Firestore instance is created without `ignoreUndefinedProperties` (`src/lib/firebase/client.ts:130`), so `setDoc` throws. The error goes only to `console.error` (`brand/page.tsx:420-421`). The form also always starts from hard-coded defaults, not the saved kit (`brand/page.tsx:155-169`), so saved values never appear after a reload.
6. **An uploaded logo breaks image generation.** The logo is stored as a base64 `data:` URL inside the Firestore document (`brand/page.tsx:190-205`), with no Storage upload. That URL is pasted into the DALL-E prompt (`imagePromptBuilder.ts:190-192`; `creativeBrief.ts:240`). DALL-E 3 prompts are limited to 4,000 characters, so every generation for a business with a logo should fail at stage 7 and be refunded.
7. **One template in three fails generation.** The frontend always sends `creativeObjective: 'conversion'` (`buildCampaignInput.ts:43`). `buildCreativeTemplateContext` throws when the template does not list that objective (`creativeTemplateContext.ts:121-123`). 10 of the 30 templates do not include `'conversion'` (`config/creativeTemplateLibrary.ts:162,201,246,418,619,678,781,886,1451,1502`), including the festival and new-launch templates. The throw happens before the pipeline's `try` block (`pipeline.ts:469-509`), so the campaign fails.
8. **The main deliverable, the poster, is visually broken.** Posters and stories are SVG files whose background is an external `<image href="signed-url">` (`compositor.ts:202`). Browsers do not load external subresources inside an SVG shown through `<img>`/`next/image`, so the preview shows text on a dark gradient with no photo. "Download" saves this SVG under a `.png` name (`CampaignDetailContent.tsx:313`). Every URL is a V4 signed URL that expires after 7 days (`generatedAssetStorage.ts:50-54`).
9. **Storage signing is blocked by IAM in production.** On 2026-09-22 production `getUploadUrl` returned 500 with `Permission 'iam.serviceAccounts.signBlob' denied` (Phase 19C, Continuation 3). Product creation requires a photo, and AI hero images are re-hosted with signed URLs, so both depend on this grant. I found no later evidence that it was fixed, so it stays BLOCKED/UNKNOWN.

**The single most important question: is Business Brain data actually used?** Partly, and in a lossy way. `generateCampaignStrategy` reads fresh Firestore data on every call: `businesses/{id}` (`:171`), `brand_kits/{id}` and the product (`:231-234`). It does **not** read a stale cache. But:

- The persisted `businessBrain` is dumped as JSON into an AI "Business Understanding" prompt (`pipeline.ts:1211-1228`). The facts that later stages use, including the copy prompt's "BUSINESS FACTS (IMMUTABLE)" (`pipeline.ts:1385`) and Truth Check's operations, hours, minimum-order and delivery-radius checks (`truthCheck.ts:1427-1428,1528,1564,1606`), are the **AI's re-extraction**, not the stored values. So business understanding is regenerated by AI on every run, even though it starts from real data.
- `businessBrain.identity` (name, description, location, contact) is written once at onboarding (`createBusiness.ts:151-157`) and **never updated**. `updateBusiness` writes only the top-level fields (`updateBusiness.ts:70-77`). Stage 1 (`pipeline.ts:1217`) and the template context (`creativeTemplateContext.ts:169-175`) read `identity`, so an edited name, phone, address or description never reaches those parts of generation. The top-level `description` is never passed to the pipeline at all.
- `businessBrain.brand` (default colours and tone from onboarding) competes with `brand_kits`. The wizard sends `localization.brandTone` from `businessBrain.brand.tone` (`buildCampaignInput.ts:78`), while the copy prompt uses the brand kit's tone (`pipeline.ts:1389`).
- `businessBrain.products` is always `[]` (`createBusiness.ts:158`), so the catalogue in the Brain is never populated.
- The client-side `getBusinessBrainContext` (`src/features/business-brain/services/businessBrainService.ts`) has no callers. It is dead code.
